The new-pllm tool is a rewrite of the original pllm tool, preserving the same functionality while improving code quality, readability, and maintainability. The core purpose remains identical: given a Python snippet, the system uses a large language model (via Ollama) to identify the required Python version and third-party modules, queries PyPI for compatible versions, builds a Docker container with those dependencies, runs the snippet inside it, and iteratively resolves any errors by prompting the LLM to suggest fixes.

The most significant structural change is in the LLM error-handling logic. In the original code, the methods for handling ImportError, ModuleNotFoundError, AttributeError, and SyntaxError each contained nearly identical blocks of code that followed the same pattern: extract the offending module name from the error, fetch available versions from the cache, and ask the LLM to pick a new version. In the new version, this repeated logic has been consolidated into a single shared method, and each specific error handler now simply provides its unique prompt template and delegates to that shared method. This eliminates roughly two hundred lines of duplicated code and makes future changes much easier since any fix to the resolution logic only needs to happen in one place.

Method names throughout the codebase have been renamed to be more descriptive and follow standard Python conventions. For example, the error-tracking method previously called "naughty_bois" is now called "record_error", the method that applies an LLM-suggested fix was renamed from "update_llm_eval" to "apply_fix", and the module reordering method was changed from "shuffle_modules" to "reorder_modules". Internal helper methods now follow the underscore-prefix convention to indicate they are private.

In the main orchestrator, the error type dispatching logic has been simplified. The original had a long chain of if-elif branches where five different error types all executed the exact same three lines of code. The new version groups these identical cases into a single branch using a tuple check, making the flow much easier to follow.

The Dockerfile generation has been cleaned up to use a list-based approach for building lines rather than repeated string concatenation with inline comments. The Docker image tag prefix was changed from "test/pllm" to "test/new-pllm" so both versions can coexist without conflicts. The default LLM model in the command-line arguments was updated from "phi3:medium" to "gemma2" to reflect the model that was actually being used in practice.

Several unused elements were removed across the codebase. The original files contained commented-out code blocks, unused imports such as sys and BytesIO, Pydantic schema classes that were defined but never referenced, and roughly eighty lines of hardcoded test error strings that had been used during development. The Docker container image was also slimmed down by removing Python packages like transformers, accelerate, jq, and llama-index-llms-ollama, which were not used by any of the helper scripts and were leftover from earlier experimentation. This makes the container build faster and the image smaller.

File handling was improved by replacing raw open and close calls with Python context managers throughout the logging code, ensuring files are properly closed even if an error occurs during writing.

Beyond code quality improvements, the new version also includes performance and accuracy optimizations that change the resolution strategy from an LLM-first approach to an algorithm-first approach with LLM fallback. The original system relied entirely on the LLM for two critical tasks: extracting the offending module name from an error message, and selecting which version to try next. Both of these are prone to LLM hallucination, where the model might return a module name that does not exist or suggest a version number that was never published on PyPI.

To address this, the new version introduces a regex-based error parser that runs before the LLM is ever called. This parser uses a collection of regular expression patterns to extract module names directly from common Python error formats such as ModuleNotFoundError, ImportError, AttributeError, and pip version resolution failures. Since these error messages follow predictable patterns, the regex extraction is both faster and more reliable than asking the LLM to interpret the same text. The LLM is only consulted as a fallback when the regex patterns fail to match, which typically happens only with unusual or ambiguous error messages.

For version selection, the original system asked the LLM to perform "equally distanced sampling" over a list of available versions, which frequently resulted in the LLM picking versions that did not exist in the cached list or repeating versions that had already failed. The new version implements an algorithmic version selection strategy that deterministically picks versions using a midpoint sampling approach. It starts with the latest version, then the second-latest, and then uses binary-search-style midpoint sampling to cover the version space efficiently. This eliminates the randomness of LLM-based version picking and ensures every suggested version actually exists in the cached PyPI data.

Additionally, all LLM-suggested versions now go through a validation step that checks them against the actual cached version list before they are applied. If the LLM suggests a version that does not exist, the system automatically finds the closest valid version in the list rather than attempting a Docker build that is guaranteed to fail. This prevents wasted build cycles on invalid versions.

The main orchestrator now includes a per-module error counter that tracks how many times each module has caused consecutive identical errors. If a module fails the same way three times in a row, it is automatically removed from the dependency list rather than continuing to loop indefinitely. This prevents the system from getting stuck on modules that are fundamentally incompatible with the target Python version or platform, which was a common failure mode in the original implementation.
